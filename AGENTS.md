# Durable rules
- Unprivileged NixOS LXC only; Immich first; standard Intel render-device sharing.
- Replace disposable images; no routine production nixos-rebuild or deploy-rs.
- Publish one image per service. Fresh roots lack the root-local operational activation record; activate explicitly after enrollment/restoration and identity-exclusivity checks. Keep activation state on the disposable root, outside persistent backups; never infer permission to start from restored files or version markers.
- Persist data and identity only on declared volumes. /persist stays on NVMe; /data contains only bulk originals suitable for HDD migration. Keep DBs, thumbnails, previews and encoded video on /persist.
- GitHub builds/releases only; no homelab credentials or administrative access.
- Operators pull explicit verified releases. MVP provisioning/replacement is manual.
- Tailscale-only access; preserve confinement and Secure Boot.
- Read-only host discovery is allowed. Mutations confined to designated test containers and verified disposable test volumes are permitted without further approval. Storage authorization requires a creation record identifying the exact volume; container IDs, names and current attachment alone are insufficient. Before storage mutations, verify provenance and attachments. Never include production volumes, retained recovery data or sole backups. If verification is incomplete or inconsistent, ask for approval. Changes to the underlying Debian/Proxmox host, shared infrastructure or production resources require explicit approval of a detailed, bounded execution plan, not individual commands.
- Before requesting approval, complete available read-only discovery and prepare a concrete plan. Identify the exact target resources and provenance, intended outcome, ordered changes, data/credential/publication effects, downtime, material risks, preserved recovery copies, failure/recovery steps, stop conditions and verification criteria. Keep live identifiers in the private operator plan, not this public file. Broad goals such as "go productive" do not substitute for approval of this plan.
- Approval authorizes implementation details, command selection, retries and equivalent fixes within the plan's explicit resource, permission, data and availability boundaries. Do not ask again merely because a command or filesystem path must change. Recheck live preconditions before mutations and retain private execution receipts. Stop and request a revised plan approval if targets or privileges expand, additional host/shared-infrastructure changes are needed, data-loss/exposure or downtime exceeds the approved scope, recovery protection weakens, or provenance becomes uncertain. Plan approval never waives the storage/deletion prohibitions above and below.
- Never put plaintext secrets in Git, images, the Nix store, or logs.
- Enroll Borg credentials as root-only runtime files on /persist, independent of images. Keep one independently verified 1Password Borg recovery Document per service; omit the resettable Storage Box enrollment password. Retain legacy age recovery material until migration and restoration are proven.
- Require consistent backups before migration-bearing updates.
- Keep imports explicit and modules simple; test replacement and restoration.
- Never delete persistent storage outside verified disposable test volumes, or assume software rollback reverses migrations.

# Secret handling
- Use only the `Homelab` 1Password vault for all reads and writes; always select it explicitly and never access other vaults.
- Never display secret values or load them into model context, chat, tool results, screenshots, clipboard, logs or receipts. Do not inspect credential files or recovery Documents with commands that print their contents. Authorized backup, restore, enrollment and verification programs may read secret bytes internally and transfer them directly between approved endpoints; this is not permission to expose their values.
- Prefer metadata-only discovery and allowlisted schema/public-key inspection. Verify secret equality with a silent comparison and report only success/failure; do not print secret hashes, excerpts, lengths or encoded values. Redacting output after capture is not a substitute for preventing capture. Restrict 1Password operations to the intended service Document; do not enumerate unrelated secrets.
- Generate and populate credentials with trusted local programs, protected file descriptors or direct authenticated file transfers. Never put secret values in command arguments, shell substitutions, exported environment variables, Nix expressions, source patches, tool arguments or prompts to the user. Disable shell tracing and verbose/debug payload logging; ensure failure output cannot include credential contents. Use synthetic credentials in tests and CI.
- Set umask077 before creating plaintext. Use an explicitly identified mode0700 staging directory outside the repository and Nix inputs; create private files mode0600 from the outset. Verify the destination volume, parent ownership, permissions and absence of symlinks before writing. Install as root:root under /persist/secrets with mode0700 directories and mode0600 files; use a same-filesystem atomic installation that refuses existing targets for initial enrollment. Rotation requires an approved replacement/recovery plan; never silently overwrite credentials.
- Assemble the single Borg recovery Document locally from protected files without printing values. Transfer it directly to the intended 1Password item, or hand the protected file to the operator; never use chat or clipboard as transport. Independently retrieve it into protected storage and verify repository access/restoration with status-only output. Remove temporary plaintext only after verified escrow; preserve sole recovery copies and legacy material required by retained releases. If exposure is suspected, stop, report affected credential types/locations without values, and obtain direction for rotation.

# Repository rules
- `modules/` contains reusable NixOS modules with typed options; never import a service deployment or hardcode its ports, paths or service names there.
- `services/<name>/` owns application configuration, package overrides, patches, backup hooks and application tests. `deployments/` composes explicit imports and operator resource contracts. `lib/` contains small construction helpers; `flake.nix` registers outputs explicitly.
- Keep upstream NixOS modules where practical. Document local patches with their rationale, regression check and removal condition. Avoid automatic directory imports and speculative frameworks.
- Backups may keep the application offline for the entire Borg operation. Prefer direct reads of quiesced state over duplicate media staging. Dump databases logically, exclude their live files, attempt every required restart on failure, and preserve recovery intent when restart fails.
- Work on short-lived branches and submit a PR with required CI checks before merging to main. Release only an exact main commit with successful checks; publication and deployment are distinct operations.
- `VERSION` is repository SemVer, initially 0.1.0. Never modify an existing release/tag. Keep upstream application versions and storage-contract versions separate. Compatibility covers manifests, output names, persistent paths/markers, ownership, secret requirements and recovery procedures. Document migrations explicitly; version numbers do not promise database rollback safety.
- Build image archives on separate runners (at most three concurrent), not concurrently on one runner. Preserve the stable `Required checks` gate; failed/cancelled dependencies must fail it and an empty image selection must skip builds safely.
- CI compares evaluated image/check derivations with the base commit; unavailable base means build all. Current evaluation failures fail CI. Cache misses rebuild normally. Keep docs and Git revision metadata out of runtime image inputs unless required.
- Validate formatting, shell, application hook failure recovery, storage guards, secret handling and affected Linux systems/images. ARM macOS evaluates/lints; GitHub builds Linux. Rehearse full restoration before production.
- Keep docs current and compact. `docs/validation.md` is the verification matrix; history is in Git. Live GUID inventories, node/account identities, credentials and recovery receipts stay outside this public repository. Never treat historical test records as live storage authorization.
- Pin supported GitHub action releases by immutable commit; audit JavaScript runtimes and composite children when upgrading actions. PR caches must remain isolated from main/release trust.
